## Failure-mode analysis

The model **does not hallucinate brand names** in this eval — the Chat-5
brand-blocklist sanitizer plus the EVIDENCE-ONLY system prompt held. The
remaining failure mode is more interesting and worth documenting honestly.

**Failure mode: specific-detail confabulation under sparse evidence.**

When the alert payload is one line (e.g. `KafkaConsumerLagHigh lag=15000`)
and the retrieved runbook chunks describe general remediation steps rather
than this specific incident, the fine-tuned model still produces a fully-
formed postmortem with:

- Invented timestamps (`2022-08-02 14:25 UTC`)
- Invented pod names and node identifiers
- Invented root causes (`a bug in the consumer group implementation caused an infinite loop in rebalance`)
- Invented remediation steps presented as historical fact

The grader correctly flags every one of these as unsupported. Worst-case
rows score 0/16 and 0/19 supported claims.

**Why this happens.** The model was QLoRA-fine-tuned on ~2,000 real public
postmortems, all of which contain specific timestamps, named services, and
concrete root causes. It learned that "postmortem" entails specifics. When
evaluation contexts don't contain those specifics, the model defaults to
invention rather than abstention or placeholders. This is consistent with
known LLM behavior on RAG with sparse retrieval — fluency-trained models
prefer producing plausible specifics over admitting absence.

A secondary artefact appears in row 006: the string `<PERSON>-macbook-pro`
leaks through as a node name. This is an unscrubbed Presidio placeholder
from training data that the model memorised as a literal token.

## Why we are accepting 0.63

A second iteration on the system prompt was the obvious next move and
remained on the table. We chose to accept the 0.63 number for two reasons:

1. **Honesty over hand-tuning.** The failure mode above is a real, well-
   understood limitation of fluency-trained generation under sparse RAG.
   A model card that names it precisely is more defensible in an interview
   than a marginally-higher score chased through prompt iterations against
   the same 20-case set. Score-chasing on the eval set is the textbook
   wrong move.

2. **Operational cost.** The Groq free-tier TPD ceiling for the 70B grader
   is 100K tokens / rolling 24h. Tonight's grading run consumed 67K. A
   prompt-iteration loop would require: regenerate the 20 outputs against
   the new prompt (~$0.30 Modal A10G time, fine), then re-grade — which
   needs another ~67K of 70B budget. The TPD window does not fully reset
   for ~24h. Day-4 grading was already stalled by ~36h waiting for budget
   to decay (handoff Chat-5 → Chat-6); spending another 24h waiting for a
   second iteration that may or may not clear the threshold is a poor
   trade against starting Week-4 deployment work. Path C (Hybrid) — 8B
   inner-loop in CI plus periodic 70B canonical runs — is built in Week 4
   precisely to make iteration cheap. Iterating now under the unmitigated
   constraint is the wrong sequence.

The number is what it is, and it is faithfully reported.

## What changes in Week 4–5

- The Path-C 8B-instant inner-loop (built in Week 4) lets us iterate
  prompts with sub-second feedback rather than 24h. If a future iteration
  clears 0.75 on the 8B proxy and we can confirm with a 70B canonical
  run, that becomes the headline number and this section is updated.
- The `<PERSON>-macbook-pro` token leak suggests at least one training
  example escaped Presidio scrubbing. Worth a one-line audit of the
  scrubbed corpus before any future fine-tune.
- The score-0 rows cluster on alerts where retrieval surfaces only
  general runbooks (Kafka lag, k8s service-account misconfigs).
  Retrieval expansion or query rewriting in the agent could move the
  needle more than further prompt iteration on the generator.
